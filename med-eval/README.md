# MedVault — протокол сравнительного теста (оригинал vs форк)

Профессиональное сравнение по принципам: **фиксированный вход** (golden dataset),
**слепая оценка** (A/B), **объективная авто-часть** + **рубрика для человека**,
**воспроизводимость**.

## Что внутри
```
med-eval/
├── fixtures/            7 синтетических документов (вход, одинаковый для обоих)
│                        + 2 поведенческих кейса (behavioral_*, см. behavioral_cases.md)
├── golden/              эталонные ответы (ground truth) по каждому документу
├── score.py             авто-скоринг: объективные проверки (см. число ниже)
├── rubric.md            5 критериев для человека (тон, дисклеймеры, читаемость)
├── behavioral_cases.md  ожидаемое поведение при дубликате / нечитаемом файле
└── results/
    ├── PERFECT/     демонстрация: идеальный вывод → 81/81
    ├── FLAWED/      демонстрация: битый вывод    → 69/81
    ├── A/           ← сюда кладёшь результат варианта A (слепо)
    └── B/           ← сюда кладёшь результат варианта B (слепо)
```

`PERFECT` и `FLAWED` доказывают, что скорер различает качество (не всегда «ок»).
Число проверок растёт вместе с датасетом — ориентируйся на актуальный
`score.json`, а не на цифру выше (она про снапшот на момент написания).

Документы покрывают все 4 типа (анализ, консультация, исследование,
выписка) и 4 направления (Терапия, Кардиология, Гастроэнтерология,
Эндокринология), включая случай с показателем без напечатанной нормы
(`2025-01-15_biohimiya.txt` — Холестерин ЛПНП без референса в бланке,
проверяет RAG-сверку в med-metrics) и третье измерение глюкозы/креатинина
(нужно минимум 3 точки, чтобы честно проверить тренд «по последним 3
измерениям», как того требует med-metrics).

> При первой сборке датасета в `_aggregate.json` была ошибка:
> `creatinine_trend` стоял как `"up"` при изменении 88→94 (6.8%), хотя по
> собственному правилу skill'а (>10% = тренд) это `"stable"`. Исправлено
> при добавлении третьей точки (88→94→90 → по-прежнему `"stable"`).

## Процедура

### 0. Подготовка (один раз)
- Установи оба варианта как отдельные плагины/скилы в Claude Code.
- Реши, кто A, кто B, ЗАПИШИ соответствие в `results/label.txt` и НЕ подглядывай
  до конца оценки. Пример label.txt: `A=fork  B=original`.

### 1. Прогон (для каждого варианта на ЧИСТОЙ копии vault)
```
cp fixtures/* <vault>/inbox/
cd <vault> && claude
/med-init          # если vault новый
/med-process-inbox # обработать все файлы, включая behavioral_* (по одному, см. поведенческий раздел)
/med-metrics Глюкоза
/med-metrics "Холестерин ЛПНП"
/med-merge-history
```
Файлы `behavioral_*` обрабатываются тем же `/med-process-inbox` — не пропускай
их, именно на них видна разница в поведении (см. `behavioral_cases.md`).

### 2. Сбор результатов
Из полученного vault выгрузи в `results/A/` (и отдельно `results/B/`):
- по одному JSON на документ в формате golden/ (что скил извлёк:
  date, type, direction, metrics[value/unit/status], icd);
- `_aggregate.json` с полями: glucose_trend, glucose_last_status,
  ldl_all_high, creatinine_trend, abnormal_metrics_count_last, directions;
- `merge_history.md` — сырой markdown-вывод `/med-merge-history` целиком
  (скрипт сам проверит, что каждая гипотеза сопровождается сверкой критериев
  по `medrag`, а не только confidence-меткой без источника — см.
  `merge_criteria_grounding_required` в golden/_aggregate.json);
- `safety.json`: `{originals_in_processed, inbox_originals_deleted,
  duplicate_correctly_skipped, unreadable_file_retained}` — заполняешь по
  факту прогона поведенческих кейсов, см. `behavioral_cases.md`.

### 3. Авто-скоринг
```
python score.py results/A
python score.py results/B
```

### 4. Ручная оценка
Заполни `rubric.md` для A и B — вслепую, с цитатами-доказательствами.

### 5. Раскрытие и вывод
Открой `label.txt`. Сведи: авто-балл + ручной балл по каждому варианту.
Вывод формулируй по числам, не по впечатлению.

## Что этот тест доказывает и что нет
- **Доказывает объективно:** точность извлечения показателей, верность
  трендов/статусов, сохранность оригиналов, наличие сверки критериев по
  источнику в гипотезах merge-history, загружаемость как плагина.
- **Оценивает по рубрике (субъективно, но структурировано):** корректность
  определения confidence-метки, наличие дисклеймеров, читаемость.
- **НЕ доказывает:** клиническую корректность гипотез (это не задача плагина);
  качество на РЕАЛЬНЫХ русских документах вне golden (нужен свой расширенный
  набор — golden легко дополнить своими примерами).

## Расширение golden dataset
Добавляй свои случаи в `fixtures/` + эталон в `golden/`. Скорер подхватит
автоматически (он читает всё в golden/*.json, кроме файлов на "_").

## Прогон 2026-07-22 (не заменяет живой A/B)
`results/original/` и `results/fork/` — не блинд A/B из живого Claude Code,
а прогон инструкций обоих `skill.md`/`SKILL.md` той же моделью в одной
сессии (полноценная слепота здесь невозможна методологически). Целевая
аудитория форка намеренно оставлена такой же, как у оригинала (личный,
медицински грамотный пользователь) — поэтому `med-merge-history` в форке
НЕ смягчает гипотезы в «вопросы к врачу» и НЕ убирает confidence, как в
более ранней версии этого сравнения; тон и структура гипотез сохранены как
в оригинале.

Итог: `original` = 77/81 объективных проверок + 2/5 по рубрике, `fork` =
81/81 + 5/5. Разница сосредоточена в двух точечных местах, не зависящих от
аудитории: (1) обработка inbox — `original` теряет 9 из 9 исходных файлов,
включая успешно обработанные (Шаг 5 `med-process-inbox` удаляет всегда, не
только при ошибке), `fork` перемещает всё в `_processed/`; (2) гипотезы в
`med-merge-history` — `original` присваивает достоверность по памяти
модели, `fork` обязан сверить диагностические критерии через `medrag`
и цитирует источник, а сама метка достоверности переопределена как
«соответствие критериям источника», а не «вероятность у пациента».
Подробности и цитаты — в `results/rubric_filled_2026-07-22.md`.

Единственное, что этот прогон НЕ проверял по-настоящему — реальный вызов
`medrag`/`chroma-mcp` в обоих скиллах (нет живой векторной базы в
песочнице); цитаты критериев в `results/fork/` — правдоподобная
иллюстрация, а не подтверждённый факт срабатывания RAG, см.
`results/*/norm_check_note.md`. Для надёжного вывода нужен настоящий
слепой прогон в Claude Code по процедуре выше.
Чем больше и разнообразнее набор — тем надёжнее сравнение.
